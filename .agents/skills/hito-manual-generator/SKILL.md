# hito-manual-generator

## 目标

基于前后端代码库，为指定功能自动生成结构化的用户手册(.md 格式)，用于支持 LangChain 检索增强生成（RAG）分块（chunking）后向量化落库。

## 强制约束

- 文档保存到项目根目录的 `manual/` 目录下。
- 不要编造代码中不存在的功能。所有描述必须有代码依据。
- 如果代码中没有发现与用户描述匹配的功能，明确告知用户并停止。

## 工作流程

### 第一阶段：读取前后端代码库，理解业务逻辑

#### 第一步：理解喜多核心业务

「喜多」是一个 SaaS 架构的私域活动管理平台。系统采用多租户隔离，核心业务逻辑自顶向下分为三层：`社区` -> `社团` -> `活动`，其中活动分为普通的 `活动` 和 `历史活动` 两类。

1. 组织架构关系：
   - `社区` 与 `社团` 为 一对多（1:N）关系。
   - `社团` 与 `活动` 为 一对多（1:N）关系。
2. 活动分类与代码映射：
   - `活动`（代码标识：`CIE`）：支持正常的用户报名与签到打卡功能。
   - `历史活动`（代码标识：`CE`）：由社团管理员点击“补充历史活动”手动补充，不可报名/打卡，一般仅用于社团历程展示。
3. 各层管理员角色如下表：

| 中文名称   | 代码库常用缩写 | 说明                                           |
| ---------- | -------------- | ---------------------------------------------- |
| 全局管理员 | GA             | 平台级最高权限，跨租户管理                     |
| 社区管理员 | TA             | 租户级管理员，管理租户（社区）下所有群组和活动 |
| 社团主理人 | CO             | 社团拥有者，对社团拥有完整管理权限             |
| 社团管理员 | CA             | 社团管理员，拥有社团内部分管理权限             |

其中社团主理人必定也是社团管理员。一个社团（crowd）中只能有一个社团主理人，但可以有多个社团管理员。当一个活动被创建时，创建活动的社团管理员默认成为该活动的活动管理员。

**确保完全理解以上业务逻辑、层级关系及各角色名称，再编写操作手册。**

#### 第二步：阅读前端代码

通过 `hito-codebase-reader` skill 阅读前端相关代码，读取每个页面的文件，理解前端页面布局和操作流程，重点关注：

- 页面标题和导航栏文案 → 用于确定功能在 UI 中的名称
- 数据加载逻辑(onLoad / fetchData 等方法) → 用于了解功能的输入条件和加载流程
- 用户交互方法(tap、submit 等) → 用于编写操作步骤
- 条件分支(if/else、disabled、角色判断) → 用于编写权限和约束说明
- 提示文案(toast、modal、empty state) → 用于了解边界情况和错误提示
- 后端API接口信息（路径、request method） → 用于理解后端业务逻辑

#### 第三步：阅读后端代码

通过 `hito-codebase-reader` skill 阅读前端调用的后端 Controller 接口，并沿调用链路向下深挖，理解后端业务逻辑和数据查询方式，重点关注：

- 接口定义：请求路径、HTTP 方法、入参（Body/Query）以及鉴权注解（如 @ServiceResource）。
- 权限与校验：允许操作的角色（如 assertCrowdOwner/Admin）和业务约束（如名称唯一、数量上限、状态流转）。
- 核心业务处理：
  - 写操作：进行了那些校验，抛出了哪些异常，以及最终修改、创建或删除了哪些对象的哪些字段。
  - 读操作：查询的过滤条件、分页机制以及数据的聚合/组装方式。

### 第二阶段：根据代码中呈现的业务逻辑，编写用户手册

在完整分析前后端代码后，按以下固定结构编写文档。

#### 编写原则

1. **面向终端用户**：文档面向用户， **严禁** 使用任何技术语言（包括代码路径、方法名、变量名等技术术语）。
2. **操作步骤有起点**：每个操作场景必须从根路径对应的功能入口开始导航，使用产品语言描述导航链路，不写页面路径。
3. **所有描述必须有代码依据**：操作步骤来自前端方法的执行流程，业务规则来自后端 CommandHandler 的校验逻辑。
4. **场景覆盖完整**：根据前端页面的条件分支，覆盖所有角色视角下的操作流程。
5. **权限、约束、FAQ 随场景走**：每个操作场景的 `###` 下必须包含该场景的角色权限说明、业务限制和常见问题，不要单独抽成独立章节。
6. **FAQ 从错误中来**：所有常见问题的答案都能在代码的 `throw Ex.of(...)`、`showToast`、`wx.showModal`、空状态文案中找到依据。

#### 操作入口根路径

编写操作指南时，根据功能所属模块从以下根路径对应的代码目录开始追踪导航链路：

| 功能入口   | 根路径                                                      | 代码追踪起点                                           |
| ---------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| 社区首页   | `/pages/index`                                              | 社区整体入口                                           |
| 群组首页   | `/pages/crowd`                                              | 群组维度的管理入口，渠道管理、成员管理等功能从此进入   |
| 活动详情页 | `/pages/hito/ce-detail` 或 `/pages/clockin/clock-in-detail` | 活动维度的入口，渠道码、签到、问卷等活动级功能从此进入 |

- 操作步骤必须从指定根路径开始导航，不能跳步。
- 操作入口使用产品语言描述导航路径(如"社区首页 → 选择群组 → 渠道管理")，文档中不写任何页面路径。
- 路径仅用于 agent 在代码分析阶段定位页面文件，生成文档时只保留文案。

#### 文档结构

生成的文档开头必须包含 YAML front matter，正文必须遵循固定的三章节结构（概述、核心概念、操作指南），其中操作指南按功能场景拆分为多个自包含的 `###` 小节。每个 `###` 标题必须是一个自包含的 RAG chunk 单元，包括该场景对应的 `角色权限`、`操作入口`、`操作流程`、`限制与约束` 和 `常见问题`。

##### Front Matter 字段说明

| 字段         | 类型   | 说明                                                                                                         |
| ------------ | ------ | ------------------------------------------------------------------------------------------------------------ |
| `title`      | string | 功能中文名，与正文一级标题一致                                                                               |
| `updated_at` | string | 文档生成/更新时间，格式 `YYYY-MM-DD HH:mm:ss`，必须通过 `date "+%Y-%m-%d %H:%M:%S"` 命令获取系统当前真实时间 |
| `version_fe` | string | 对应的前端版本号，通过 `hito-version-getter` skill 获取                                                      |
| `version_be` | string | 对应的后端版本号，通过 `hito-version-getter` skill 获取                                                      |

### 第三阶段：自检复核

生成文档后，逐项核对以下清单，确保质量：

1. **面向终端用户**：文档面向用户， **严禁** 使用任何技术语言（包括代码路径、方法名、变量名等技术术语）。
2. **代码依据检查**：文档中每个操作步骤、权限声明、业务约束是否都能在代码中找到对应依据？逐条回溯确认。
3. **权限一致性检查**：角色权限表格中每个角色的权限声明是否与后端鉴权逻辑一致？
4. **完整性检查**：是否覆盖了前端条件分支中的所有角色视角（GA / TA / CO / CA）和边界状态（空数据、加载中、错误）？
5. **Front Matter 检查**：文档顶部是否包含 YAML front matter？其中的字段是否完整？

发现不符合项时，回到对应代码补充分析后修正，不要直接发布。

## 输出产物

最终文档保存到 `manual/{功能英文名}.md`，例如:

```
manual/channel-code.md
```

文件名使用功能英文名(小写，连字符分隔)，与代码中的模块名保持一致。

生成完成后，输出文档路径和章节摘要，告知用户文档已生成。
