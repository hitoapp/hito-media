# xiaohongshu-publish

## 目标

围绕喜多（HITO）产品宣传完成两类工作：

1. 基于 `hito-mp` 代码仓库的版本改动，总结产品特性、运营价值和用户场景，生成小红书内容。
2. 当用户明确要求发布小红书时，使用用户本机 Chrome 登录态，在小红书创作服务平台发布图文笔记。

默认内容目标是展示喜多产品专业度、解释新功能，并向现有客户说明产品解决了哪些具体问题。优先把技术改动转译成用户能理解的产品价值，不直接堆提交信息。

## 强制约束

- 发布小红书必须使用用户本机 Chrome，因为登录态在 Chrome 中。
- 小红书发布流程优先使用 Computer Use 操作页面。
- 不要使用普通内置浏览器完成小红书发布。
- 不要把 DOM 脚本注入、`evaluate`、`domSnapshot`、脚本级 `filechooser` 作为小红书发布主路径；小红书创作页上这些方式可能超时或卡住。
- 只有用户明确要求“发布”“发送”“帮我发出去”时，才点击发布。
- 如果用户只要求生成或准备内容，停在内容草稿或预览检查阶段，不点击发布。
- 发布前必须检查右侧预览或页面状态，确认图片、标题、正文已经出现。
- 发布成功后保留 Chrome 页面给用户查看。

## 关联代码仓库前置检查

每次生成小红书内容前，必须先分析喜多产品代码仓库。

关联仓库固定为：

```text
git@github.com:hitoapp/hito-mp.git
```

本地路径固定为当前媒体仓库下：

```text
.tmp/hito-mp
```

执行规则：

1. 确认当前媒体仓库的 `.gitignore` 包含 `.tmp/`。
2. 如果 `.tmp/hito-mp` 不存在，提示用户需要先克隆该仓库，或执行：

   ```sh
   mkdir -p .tmp
   git clone git@github.com:hitoapp/hito-mp.git .tmp/hito-mp
   ```

3. 如果 `.tmp/hito-mp` 已存在，先执行：

   ```sh
   git -C .tmp/hito-mp pull --ff-only
   ```

4. 如果拉取失败，停止生成并向用户说明失败原因。
5. 拉取成功后执行：

   ```sh
   git -C .tmp/hito-mp tag -n
   ```

   如果需要展示 tag 日期和 commit 信息，使用：

   ```sh
   git -C .tmp/hito-mp for-each-ref --sort=-creatordate --format='%(refname:short)|%(creatordate:short)|%(subject)|%(objectname:short)' refs/tags
   ```

6. 忽略没有 `v` 前缀、但语义上与 `v` 版本重复的 tag。例如 `1.9.4` 与 `v1.9.4` 同时存在时，只保留 `v1.9.4`。
7. 如果存在 tag：
   - 用表格列出全部有效版本，至少包含版本号、tag 日期、tag 说明、对应 commit 摘要。
   - 同步更新当前媒体仓库的 `docs/hito-mp-versions.md`，记录有效版本表、最新 HEAD 和更新时间，方便后续查阅。
   - 等待用户选择要宣传的版本，不要跳过用户选择直接生成正式内容。
   - 可以提示“如果你不想选，我可以默认分析最新有效 tag 与上一个有效 tag 之间的改动”，但仍要让用户确认。
   - 如果 HEAD 超过最新 tag，还要额外列出“尚未打 tag 的最新改动”。
8. 如果没有 tag：
   - 查看最近提交记录。
   - 总结最近改了什么。

## 版本分析方法

分析版本改动时，不要只看 commit message。至少结合：

```sh
git -C .tmp/hito-mp log --oneline <上个版本>..<目标版本>
git -C .tmp/hito-mp diff --stat <上个版本>..<目标版本>
git -C .tmp/hito-mp diff --name-only <上个版本>..<目标版本>
```

必要时继续查看关键文件 diff，判断哪些是真正可宣传的产品改动，哪些只是技术优化或重构。

输出给用户时，先给“可宣传改动候选清单”，等待用户决定内容方向。候选清单应包含：

- 版本范围
- 技术改动摘要
- 可宣传的产品特性
- 对用户或运营者的价值
- 适合的小红书内容风格
- 建议配图方向

## 内容生成要求

生成正式内容前，不要直接给最终稿。先输出“内容策略确认卡”，让用户逐步确认方向。

### 内容策略确认卡

默认先给用户以下选项和建议：

- 发布目标：默认“展示产品专业度 + 解释新功能 + 服务现有客户”。
- 目标读者：结合改动判断，常见读者包括社团负责人、活动运营者、组织管理者、合作方或已有客户。
- 小红书默认风格：产品更新日志。
- 小红书可切换风格：创业者分享、客户案例、活动运营干货、轻量种草。
- 内容类型建议：结合版本改动，从产品更新、功能教程、场景问题、客户案例、避坑提醒、运营方法中选择。

策略确认卡之后，先列“候选主题”，不要直接写最终文案。每个候选主题包含：

- 主题名称
- 核心卖点
- 适合风格
- 建议配图方向
- 需要用户确认的问题

用户选择主题后，再给 2-3 种文风样稿。样稿只需要短，不要一次写成长文。用户确认标题、正文方向和配图方向后，才进入正式内容生成、图片生成或发布流程。

正式稿确认前，不要写入 `publish/` 文件夹。只有用户确认标题、正文、配图方向、平台和是否发布后，才创建发布目录并保存文件。

### 小红书

小红书内容应更口语、更场景化，突出一个清晰卖点，适合配图传播。默认使用“产品更新日志”风格，写作时像是在认真说明一次产品能力升级，而不是写内部版本说明。

生成小红书内容时，借鉴小红书运营方法，但要适配喜多的产品属性：

- 真实有用优先：不要写成硬广，不夸大功能效果，不虚构客户数据或使用结果。
- 场景先行：先讲活动组织、社团管理、报名签到、分享传播、接入方管理等真实问题，再引出喜多功能。
- 细节可信：如果有产品截图、版本 diff、真实功能入口、操作路径或后台字段，优先用这些细节增强可信度。
- 适度克制：可以表达推荐和价值判断，但避免“神器”“吊打”“必备”等过度营销词。
- 合规安全：不刷量、不诱导违规互动，不使用容易引发平台限流或误解的敏感表达。
- 避免消费品模板：不要套用“后悔没早买”“平替”“智商税”等与喜多产品气质不符的爆款话术，除非用户明确要求强种草风格。

默认输出：

- 标题候选 3-5 个
- 正文 1-2 版，或在用户尚未确认风格时先输出 2-3 种短样稿
- 话题标签建议
- 配图建议
- 发布前需要用户确认的问题

### 小红书手机端可读性

小红书正文必须优先按手机端阅读体验生成，不要写成长段落文章。

硬性要求：

- 正文默认控制在 300-450 个中文字符左右；如果功能复杂，最多不超过 550 个中文字符。
- 相比公众号或内部说明，主动压缩约 1/3 内容，只保留一个核心卖点、一个典型场景和一个产品价值结论。
- 每段 1-2 句，单段尽量不超过 45 个中文字符。
- 段落之间必须保留空行，不允许整段文字粘在一起。
- 第一屏正文应在 3-5 行内说清“这篇在讲什么”，不要用长铺垫。
- 表情可以少量使用，用来分隔节奏或强化语气；不要让表情代替产品说明。
- 标签单独放在最后一段，和正文之间保留空行。

推荐正文结构：

1. 标题式开场：一句话点出问题或更新。
2. 场景说明：说明谁会遇到这个问题。
3. 功能更新：说明喜多这次做了什么。
4. 用户价值：说明参与者、组织者或客户得到什么。
5. 收束：一句克制总结。
6. 标签：单独一段。

正式发布前必须检查正文在小红书预览中的排版：

- 如果预览或手机截图中出现大段文字粘连，必须回到正文编辑区重新分段。
- 如果正文超过手机一屏仍没有明显停顿，优先删减解释性句子，不要继续补充背景。
- 如果用户提供发布后的手机截图指出可读性问题，要把该问题总结进 skill，并在后续发布前优先规避。

建议笔记结构：

1. 痛点共鸣：用 1-2 句话说清楚活动运营者或组织管理者遇到的问题。
2. 更新引入：自然说明“这次喜多更新解决了什么”。
3. 功能说明：用具体功能点、页面变化或流程变化解释怎么解决。
4. 使用场景：说明适合哪些客户、活动或组织场景。
5. 克制总结：说明改动带来的效率、管理清晰度或体验提升，不要夸大。

可选内容矩阵：

- 产品更新：适合发布版本新能力，结构是“问题 -> 更新 -> 适用场景 -> 使用价值”。
- 功能教程：适合已有客户，结构是“入口在哪里 -> 怎么操作 -> 能解决什么”。
- 创业者分享：适合解释产品判断，结构是“观察到的问题 -> 为什么要做 -> 做成什么样 -> 后续计划”。
- 客户案例：适合有真实案例时使用，结构是“客户场景 -> 遇到的问题 -> 使用喜多后的变化”，不要虚构结果。
- 避坑提醒：适合活动运营方法论，结构是“常见误区 -> 风险 -> 喜多如何帮助管理”。

标题策略：

- 标题尽量控制在一眼能读完的长度，包含核心关键词，例如“活动运营”“社团管理”“报名签到”“分享统计”“接入方管理”。
- 默认不要使用强标题党。可以用“终于把这个问题理顺了”“这次更新主要解决一个管理细节”“活动运营后台又补了一块能力”这类真实口吻。
- 如果用户选择“客户案例”或“活动运营干货”风格，可以把标题写得更问题导向，例如“活动分享出去后，怎么知道谁真的被带来了？”

封面和配图策略：

- 优先使用产品截图、前后对比图、流程图或后台能力示意图。
- 小红书配图建议使用竖版 3:4；如果是截图拼图，要保证文字清晰，不要过度装饰。
- 封面要突出一个关键词或一句短问题，不要塞满功能点。
- 图片保持真实、清楚、可检查，不要做成过度广告海报。

标签策略：

- 使用 2-3 个较宽泛标签 + 3-5 个精准长尾标签。
- 标签围绕产品和场景，例如：`#活动运营`、`#社团管理`、`#小程序工具`、`#活动报名`、`#私域运营`、`#产品更新`。
- 不要使用与内容无关的热门标签。

发布后复盘建议：

- 如果用户要求持续运营，记录每篇笔记的发布时间、主题、标题、封面方向和数据表现。
- 复盘指标优先看阅读/曝光、点赞、收藏、评论、主页访问、私信咨询和关键词搜索反馈。
- 不要只追求单篇爆款；喜多这类产品更需要长期沉淀“活动运营”“社团管理”“小程序工具”等搜索资产。

可选风格参考：

- 产品更新日志：清楚说明这次更新解决了什么问题、适合谁、怎么用。
- 创业者分享：从“我们为什么做这个功能”切入，解释产品判断和场景观察。
- 客户案例：用一个具体运营场景讲问题、使用方式和结果。
- 活动运营干货：先讲运营痛点，再带出喜多功能作为解决方案。

所有内容都要围绕“宣传喜多产品特性或改动”，避免写成内部开发日志。

## 发布文件存放

生成内容时，按平台保存到当前媒体仓库：

```text
publish/小红书/YYYY-MM-DD-主题/
```

日期使用当前日期。主题使用简短中文短语，例如：

```text
publish/小红书/2026-06-11-接入方管理升级/
```

建议保存：

- `文案.md`
- `素材说明.md`
- `生成配图/`：封面图、正文图、产品截图、拼图或生成图片
- `发布记录.md`：发布状态、发布时间、平台链接、后续数据记录
- 如有发布后手机端截图或复盘意见，可追加到 `发布记录.md` 的“发布后复盘”部分。

写入与提交规则：

1. 先在对话中确认标题、正文、配图方向和发布平台。
2. 用户确认前，不要写入正式发布文件。
3. 用户确认后，创建对应主题目录并保存确认稿和生成配图。
4. 如果用户要求发布，必须在点击平台发布按钮前再询问一次“确认发布吗？”。
5. 发布成功后，更新 `发布记录.md`，记录平台、发布时间、发布结果和链接。
6. 发布成功并保存文件后，执行 Git 提交并推送到本仓库远端。提交只包含本次确认后的发布内容、素材和必要的仓库文档变更，不提交 `.tmp/`。
7. 如果本仓库没有配置 Git 远端，先停下来让用户提供远端地址，不要臆造远端。

## 小红书发布输入准备

正式发布前获取并确认：

1. 图片绝对路径。
2. 标题。
3. 正文。
4. 是否明确要求立即发布。

如果用户只给了文件名，先在常见目录中定位绝对路径，例如 `~/Downloads`、桌面、当前工作区。

用 `ls -l <absolute_path>` 或等价方式确认每个图片文件存在。如果图片路径不存在或不明确，先向用户确认，不要进入发布流程。

## 小红书发布流程

1. 用 Computer Use 打开或接管 Chrome。
2. 进入小红书图文发布页：

   ```text
   https://creator.xiaohongshu.com/publish/publish?source=official&from=menu&target=image
   ```

3. 如果直达链接跳到创作首页或控制台，不要反复刷新；在当前页面点击“发布笔记”或进入“上传图文”入口。
4. 确认页面处于“上传图文”页。
5. 点击“选择文件”控件，或在必要时点击“上传图片”。
6. 上传文件时，优先点击页面可访问树中的原生“选择文件: 未选择任何文件”控件。
7. 如果只能看到视觉上的“上传图片”按钮，可以尝试点击；一旦文件选择器打开，就继续使用系统文件选择器，不要再切换路径。
8. macOS 文件选择器中，优先按 `/` 打开“前往”路径输入框，输入图片绝对路径，回车选中文件，再点击“打开”。
9. 等待上传完成，直到页面出现图片预览、标题输入框、正文输入区和“发布”按钮。
10. 如果小红书请求定位权限，选择“不允许”或“一律不允许”。
11. 填写标题。
12. 填写正文。正文必须使用已确认的分段版本，保留空行；如果输入后预览中换行丢失，立即回到编辑区重新分段。
13. 检查右侧预览或页面状态，确认图片、标题、正文均已正确出现。
14. 检查正文手机端可读性：是否过长、是否有空行、是否有大段粘连、标签是否单独成段。
15. 点击发布前，必须再次询问用户确认发布；如果用户已经在当前轮明确说“直接发布”，可视为确认。
16. 用户确认后点击“发布”。
17. 如果点击后没有跳转或没有成功提示，检查按钮是否只是获得焦点；必要时按 Return。
18. 等待并确认出现“发布成功”，或 URL 跳转到 `/publish/success...`。
19. 发布成功页通常不一定提供公开笔记链接；如果页面没有直接链接，在 `发布记录.md` 中记录“暂未获取公开笔记链接”，不要臆造链接。
20. 更新本次主题目录中的 `发布记录.md`，提交并推送 Git。
21. 向用户报告发布结果。

## 异常处理

- 如果 Chrome 未登录小红书，停下来让用户登录。
- 如果上传控件不可用，先重试原生文件控件，再尝试视觉按钮。
- 如果页面卡住，不要改用 DOM 注入主路径；说明当前页面状态，让用户决定是否刷新或手动辅助。
- 如果发布失败，报告页面可见错误信息和已经完成的步骤。

## 本次实操经验

- 直达发布 URL 可能先进入创作服务平台首页；从首页点击“发布笔记/上传图文”更快，不需要反复尝试 URL。
- 文件上传路径最稳的是：点击上传入口后，在 macOS 文件选择器按 `/`，粘贴图片绝对路径，回车，再点“打开”。
- 图片上传成功后，先等标题框、正文框和发布按钮都出现，再开始填写，避免页面仍在初始化时输入丢失。
- 桌面端预览能确认图片、标题、正文是否存在，但不能完全替代手机端阅读效果；发布前要按“小红书手机端可读性”主动压缩正文并检查分段。
- 发布成功的可靠标志是页面显示“发布成功”或 URL 进入 `/publish/success...`；公开笔记链接可能不会直接出现。
