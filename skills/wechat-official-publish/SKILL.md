# wechat-official-publish

## 目标

围绕喜多（HITO）产品宣传生成微信公众号内容。默认目标是展示产品专业度、解释新功能，并向现有客户说明产品解决了哪些具体问题。

公众号内容优先服务现有客户和潜在合作方，不写成内部开发日志。把代码改动转译成客户能理解的产品价值、使用场景和行动建议。

## 默认定位

- 发布频率：默认周更。
- 默认风格：产品公告。
- 可切换风格：解决方案文章、版本更新说明、案例复盘、活动运营方法、客户问题解答。
- 默认读者：现有客户、社团负责人、活动运营者、组织管理者、合作方。
- 内容细节在写作时再确认，不预设固定比例。

## 关联代码仓库前置检查

每次生成公众号内容前，必须先分析喜多产品代码仓库。

关联仓库固定为：

```text
git@github.com:hitoapp/hito-mp.git
```

本地路径固定为当前媒体仓库下：

```text
.tmp/hito-mp
```

执行规则：

1. 确认当前媒体仓库的 `.gitignore` 包含 `.tmp/`。
2. 如果 `.tmp/hito-mp` 不存在，提示用户需要先克隆该仓库，或执行：

   ```sh
   mkdir -p .tmp
   git clone git@github.com:hitoapp/hito-mp.git .tmp/hito-mp
   ```

3. 如果 `.tmp/hito-mp` 已存在，先执行：

   ```sh
   git -C .tmp/hito-mp pull --ff-only
   ```

4. 如果拉取失败，停止生成并向用户说明失败原因。
5. 拉取成功后执行：

   ```sh
   git -C .tmp/hito-mp tag -n
   git -C .tmp/hito-mp for-each-ref --sort=-creatordate --format='%(refname:short)|%(creatordate:short)|%(subject)|%(objectname:short)' refs/tags
   ```

6. 忽略没有 `v` 前缀、但语义上与 `v` 版本重复的 tag。例如 `1.9.4` 与 `v1.9.4` 同时存在时，只保留 `v1.9.4`。
7. 如果存在 tag：
   - 用表格列出全部有效版本，至少包含版本号、tag 日期、tag 说明、对应 commit 摘要。
   - 同步更新当前媒体仓库的 `docs/hito-mp-versions.md`，记录有效版本表、最新 HEAD 和更新时间，方便后续查阅。
   - 等待用户选择要宣传的版本，不要跳过用户选择直接生成正式内容。
   - 可以提示“如果你不想选，我可以默认分析最新有效 tag 与上一个有效 tag 之间的改动”，但仍要让用户确认。
   - 如果 HEAD 超过最新 tag，还要额外列出“尚未打 tag 的最新改动”。
8. 如果没有 tag：
   - 查看最近提交记录。
   - 总结最近改了什么。

## 版本分析方法

分析版本改动时，不要只看 commit message。至少结合：

```sh
git -C .tmp/hito-mp log --oneline <上个版本>..<目标版本>
git -C .tmp/hito-mp diff --stat <上个版本>..<目标版本>
git -C .tmp/hito-mp diff --name-only <上个版本>..<目标版本>
```

必要时继续查看关键文件 diff，判断哪些是真正可宣传的产品改动，哪些只是技术优化或重构。

输出给用户时，先给“可宣传改动候选清单”，等待用户决定内容方向。候选清单应包含：

- 版本范围
- 技术改动摘要
- 可宣传的产品特性
- 对用户或运营者的价值
- 适合的公众号文章风格
- 建议配图方向

## 内容策略确认

生成正式内容前，不要直接给最终稿。先输出“内容策略确认卡”，让用户逐步确认方向。

确认卡默认包含：

- 发布目标：展示产品专业度 + 解释新功能 + 服务现有客户。
- 发布频率：默认周更。
- 目标读者：结合改动判断，常见读者包括社团负责人、活动运营者、组织管理者、合作方或已有客户。
- 默认风格：产品公告。
- 可切换风格：解决方案文章、版本更新说明、案例复盘、活动运营方法、客户问题解答。
- 内容类型建议：结合版本改动，从产品公告、功能教程、场景问题、客户案例、解决方案、活动运营方法中选择。
- 需要用户确认的问题：内容重点、文章长度、CTA、配图方向、是否需要发布。

策略确认卡之后，先列“候选主题”，不要直接写最终文案。每个候选主题包含：

- 主题名称
- 核心卖点
- 适合风格
- 建议文章结构
- 建议配图方向
- 需要用户确认的问题

用户选择主题后，再给 2-3 种文风样稿。样稿只需要短，不要一次写成长文。用户确认标题、正文方向和配图方向后，才进入正式内容生成、图片生成或发布流程。

正式稿确认前，不要写入 `publish/` 文件夹。只有用户确认标题、正文、配图方向、平台和是否发布后，才创建发布目录并保存文件。

## 公众号写作规则

公众号不是单纯广播渠道，要把内容写成对现有客户有帮助的产品说明和关系维护内容。

- 用户价值先行：先说明读者能得到什么，再说明喜多更新了什么。
- 结构清楚：标题、摘要、小标题、列表和段落都要适合手机阅读。
- 语气专业但不端着：避免内部公告腔，也避免过度销售。
- 每篇文章要有明确行动建议，例如“适合哪些客户开启”“可以检查后台哪些配置”“可以联系谁试用/开通”。
- 适合沉淀长期内容：产品公告、功能教程、客户问题解答、解决方案文章可以形成系列。
- 不虚构数据、客户反馈或转化效果。没有真实案例时，只能写“典型场景”或“适用场景”。

## 参考文风

用户过往公众号文章呈现出以下风格，以后写公众号时优先参考：

- 开篇正式、有事件感：常用“近日”“正式揭牌落地”“重要突破”“里程碑事件”等表达，先建立背景和意义。
- 价值拔高自然：会把产品功能放进更大的组织、城市、校园、绿色低碳、公共服务或长期生态价值中解释。
- 结构分节清晰：常用 `01`、`02`、`03` 分节，每节标题有明确主题。
- 标题有一定修辞：例如“让每一次低碳行动都看得见”“轻松两步，玩转你的碳积分”“携手共建绿色校园，让低碳成为新风尚”。
- 喜多角色表达克制但明确：常用“作为连接……的桥梁”“依托喜多的数据能力”“喜多很荣幸能成为……”。
- 功能说明注重用户路径：会写清楚入口、步骤、查看与兑换路径、页面位置等，让读者知道怎么操作。
- 结尾升华：从具体功能回到长期愿景，例如连接活动热情、沉淀生态价值、服务更大的战略或组织目标。
- 语言偏正式宣传稿，但需要保留可读性和操作细节，不要写成纯口号。

常用表达方向：

- “连接……与……的桥梁”
- “让每一次……都看得见”
- “将……转化为可见的……”
- “以实际行动……”
- “共同织就一张……网络”
- “不仅要连接当下的热情，更要沉淀长期价值”

使用这些表达时要结合真实功能，不要机械套用。

## 默认文章结构

默认输出：

- 标题候选 3-5 个
- 摘要
- 正文大纲
- 完整正文草稿
- 配图建议
- 发布前需要用户确认的问题

建议文章结构：

1. 摘要：用 2-3 句话说明这次更新解决的问题和适合的客户。
2. 背景问题：解释客户或运营者为什么会遇到这个问题。
3. 本次更新：说明喜多新增或优化了哪些能力。
4. 使用方式：写清楚入口、配置、操作路径或使用建议。
5. 适用场景：列出哪些组织、活动或管理场景最适合。
6. 行动建议：给出现有客户下一步可以做什么。
7. 结尾升华：把具体产品能力连接到活动运营效率、组织服务能力或长期生态价值。

## 发布文件存放

生成内容时，按平台保存到当前媒体仓库：

```text
publish/公众号/YYYY-MM-DD-主题/
```

日期使用当前日期。主题使用简短中文短语，例如：

```text
publish/公众号/2026-06-11-活动分享统计优化/
```

建议保存：

- `文案.md`
- `素材说明.md`
- `生成配图/`：封面图、正文图、产品截图、拼图或生成图片
- `发布记录.md`：发布状态、发布时间、平台链接、后续数据记录

写入与提交规则：

1. 先在对话中确认标题、正文、配图方向和发布平台。
2. 用户确认前，不要写入正式发布文件。
3. 用户确认后，创建对应主题目录并保存确认稿和生成配图。
4. 如果用户要求发布，必须在点击平台发布按钮前再询问一次“确认发布吗？”。
5. 发布成功后，更新 `发布记录.md`，记录平台、发布时间、发布结果和链接。
6. 发布成功并保存文件后，执行 Git 提交并推送到本仓库远端。提交只包含本次确认后的发布内容、素材和必要的仓库文档变更，不提交 `.tmp/`。
7. 如果本仓库没有配置 Git 远端，先停下来让用户提供远端地址，不要臆造远端。

## 公众号发布流程状态

当前 skill 先完整规定公众号内容生成、保存和 Git 归档流程。公众号后台自动发布流程尚未细化。

如果用户要求实际发布到公众号：

1. 先确认是否已经有微信公众号后台登录态和可用发布方式。
2. 先确认标题、正文、封面、摘要、原文链接、是否群发或仅保存草稿。
3. 发布前必须再次询问用户确认。
4. 如果发布流程尚未配置，不要臆造自动化步骤，先请用户补充后台入口和期望流程。
